# 11. Аналитика: текущее состояние и каталог метрик

Документ отвечает на два вопроса:

1. какую статистику уже собирает приложение и чего в ней не хватает;
2. какие метрики имеет смысл добавить по **всем отчётам фазы** и по **одному отчёту**, что из
   этого есть в Allure, а что стоит придумать под модель этого проекта.

Это проектный документ: разделы 1–7 и 10 описывают состояние и предложения, а этап 2
(аналитика фазы) уже реализован. Всё, что помечено «есть», можно проверить в текущем коде.

## 1. Что уже есть

| Уровень | Где | Что считается | Где считается |
| --- | --- | --- | --- |
| Фаза | `ReportsPage` → `ReportsSummaryChart` | Стековые полосы статусов по каждому отчёту и «накопительный результат»: сколько тестов прошли хотя бы раз из всего видимого каталога | Сервер: `ReportsService.findResultsByPhaseId` |
| Фаза (аналитика) | `PhaseAnalytics` (`/phase/:id/analytics`) | KPI, тренд pass rate/coverage, сравнение отчётов, матрица «тест × отчёт», подписи ошибок, владельцы, наборы, гигиена данных | Сервер: `PhaseAnalyticsService`, `GET /phases/:id/analytics` |
| Отчёт | `ReportDashboard` | 4 плитки (всего, процент прохождения, упавшие/сломанные, суммарное время), распределение статусов, матрица по владельцам, время по наборам, топ-8 медленных, уникальные ошибки, результаты анализа, «требует анализа», уникальные пары «причина + комментарий» | Клиент: `useMemo` по `data.results` |

Что это значит на практике:

- Страница отчётов фазы по-прежнему показывает только сводные полосы; расширенная аналитика
  вынесена на отдельный экран `/phase/:id/analytics`.
- Аналитика отчёта считает всё из одного ответа `GET /reports/:id/results`, где на каждый тест
  каталога уже выбран **один** запуск. Истории запусков, числа ретраев и переходов статусов в
  ответе нет.
- Аналитика фазы работает с сырыми запусками за период фазы: это даёт флаки, регрессы, гигиену
  и матрицу, но пока без drill-down по истории одного теста.
- Графики аналитики отчёта и фазы нарисованы собственными SVG-компонентами (`SimpleCharts`);
  `@ant-design/charts` остался в `package.json`, но больше не импортируется.

## 2. Данные, на которые можно опереться

### 2.1. Строка отчёта (`ReportResultRow`)

| Поле | Что даёт |
| --- | --- |
| `status` | `passed`, `failed`, `broken`, `skipped` или вычисленный `no_run` |
| `durationMs` | Длительность выбранного запуска; `null` для `no_run` |
| `startDate`, `endDate` | Окно запуска (ISO, UTC) |
| `owner` | Владелец запуска; `null` → «Не назначен» |
| `suiteName`, `caseName`, `path` | Группировка, имя кейса, бизнес-ключ и Java-пакет |
| `message` | Текст ошибки/падения |
| `failureReason`, `failureComment` | Ручная классификация падения и комментарий |
| `tags` | Массив тегов запуска (иначе теги каталога) |
| `circuit` | Окружение запуска |
| `inCatalog`, `catalogId`, `fullResponsibility` | Признак каталога, ID и «полная ответственность» из каталога |
| `runCount`, `passedRuns`, `failedRuns`, `recentStatuses` | Все запуски пути в окне: количество, успехи, падения и последние статусы |
| `firstStatus`, `latestStatus`, `staleGreen`, `flaky`, `retryFixed`, `regressed` | Хронология запусков и расхождения с правилом «passed побеждает» |

### 2.2. Что доступно только на сервере

`TestResult` хранит **все** запуски, а не только выбранный:

- несколько запусков одного `path` в одном окне (ретраи, повторные прогоны);
- `createdAt` / `updatedAt` — когда запись реально попала в БД;
- `projectName`, `circuit`, `tags`, `message` у каждого запуска;
- запуски, которых нет в каталоге (сейчас в отчёт не попадают).

Это открывает целый пласт метрик (стабильность, ретраи, «первый запуск против последнего»,
история падений). Для аналитики фазы read-only эндпоинт уже добавлен; для drill-down по истории
одного теста нужен отдельный `GET /reports/:id/runs?path=`.

### 2.3. Ограничения модели, которые нельзя игнорировать

1. **Правило «passed побеждает».** Если в окне есть хотя бы один успешный запуск, отчёт покажет
   `passed`, даже если последний запуск упал. Значит, статус отчёта — не «последний статус».
   Для метрик «сейчас» и «тренд» нужны сырые запуски и явное разделение:
   `reportStatus` (как в отчёте) и `latestStatus` (последний по времени).
2. **`no_run` — не статус БД.** Это вычисляемое «тест в каталоге есть, запуска в окне нет».
   Он всегда в знаменателе текущего процента прохождения, поэтому короткое окно или редкий
   прогон автоматически «портят» процент.
3. **Запуски без каталога невидимы.** `ReportsService.findResults` возвращает только видимые
   записи каталога. Запуски вне каталога хранятся, но в аналитику не попадают. Для качества
   данных это надо показывать отдельно.
4. **Отчёты могут пересекаться по датам.** Один запуск может попасть в несколько отчётов; при
   сравнении отчётов это надо учитывать, иначе «рост» в соседних отчётах — это один и тот же прогон.
5. **Идемпотентности запусков нет.** `POST /results` всегда создаёт строку; повторная отправка
   выглядит как ретрай. Метрики ретраев нужно либо чистить, либо трактовать как «повторные прогоны».
6. **Нет полей Allure.** Нет severity/priority, epic/feature/story, параметров, шагов,
   вложений, ссылок и идентификатора сборки/лонча. Часть можно эмулировать тегами и `suiteName`,
   часть требует миграции.

## 3. Ориентир: что берём из Allure

Allure Report строит отчёт вокруг статусов, категорий дефектов, наборов, владельцев, severity,
таймлайна и трендов по истории сборок; в Allure 3 есть Quality Gate, а в TestOps — обнаружение
нестабильных тестов и сравнение лончей. Полезные для нас виджеты:

| Allure | Что даёт | Наш аналог | Статус |
| --- | --- | --- | --- |
| Summary (total/passed/failed/broken/skipped) | Сводка статусов | Плитки и донат отчёта | Есть |
| Categories (Product defects / Test defects) | Разделение «дефект продукта» и «дефект теста» | `failed` / `broken` + `failureReason` | Частично |
| Suites / Packages | Разрез по наборам и пакетам | `suiteName`, префикс `path` | Есть набор, нет пакетов |
| Behaviors (epic → feature → story) | Иерархия требований | `tags` + `suiteName` | Нет иерархии |
| Severity | Критичность теста | Нет поля; можно тег `severity:*` | Нет |
| Status dynamics | Статусы по сборкам | Статусы по отчётам фазы | Частично (только полосы) |
| Duration trend | Время по сборкам | Время по отчётам | Нет |
| Retries trend | Ретраи по сборкам | Повторные запуски `path` | Нет (нужны сырые запуски) |
| Timeline | Когда что выполнялось | `startDate` / `endDate` запусков | Нет в API отчёта |
| History / Retries | История одного теста | Все `TestResult` по `path` | Нет в API |
| Test stability / flaky | Нестабильные тесты | Переходы статусов в окне фазы | Нет |
| Environment / Executors | Окружение и исполнитель | `phase.environment`, `circuit` | Частично |
| Quality Gate | Пороговые правила | Свои правила на метриках | Нет |
| Steps / Attachments / Parameters | Детализация кейса | Модель удалила `steps`; полей нет | Нет |
| Export CSV / metrics | Выгрузка | Нет | Нет |

Вывод: **80 % ценности Allure для этого проекта достижимо без изменения схемы** — на статусах,
времени, владельцах, тегах и истории запусков. Severity, шаги и вложения — отдельный этап.

## 4. Статистика по одному отчёту

**Реализовано в отчёте v2:** эффективный pass rate, покрытие, p50/p90/p95/p99, гистограмма,
нормализованные подписи ошибок, stale green, флаки/ретраи, покрытие анализом и SVG-графики
(stacked histogram, duration profile по наборам, Парето, stability/retry, owner stack).
Остальные строки таблиц — следующие шаги.

Обозначения для отчёта:

- `C` — число видимых тестов каталога (текущий `total`);
- `P`, `F`, `B`, `S` — passed / failed / broken / skipped;
- `N` — `no_run`;
- `E = P + F + B + S` — реально прогнанные тесты;
- `P + F + B + S + N = C`.

### 4.1. Исполнение и прохождение

| Метрика | Как считать | Зачем | Визуал | Приоритет |
| --- | --- | --- | --- | --- |
| Процент прохождения | `P / C` | Текущая плитка; штрафует за `no_run` и `skipped` | Плитка, донат | Есть |
| Эффективный процент прохождения | `P / E` | Качество прогона без штрафа за непрогнанное | Плитка рядом с текущим | P0 |
| Покрытие исполнением | `E / C` | Сколько каталога реально прогнано | Плитка/bullet | P0 |
| Доля пропусков | `S / E` | `skipped` часто скрывает непройденные сценарии | Плитка + топ наборов | P1 |
| Доля `no_run` | `N / C` | «Слепые зоны» отчёта | Плитка + список | P0 |
| Зелёный, но последний запуск упал | `reportStatus = passed` и `latestStatus ∈ {failed, broken}` | Показывает цену правила «passed побеждает» | Счётчик + список | P2 (после API истории) |
| Прохождение с первого запуска | `firstStatus = passed` | Отличает стабильный тест от «зелёного после ретрая» | Плитка | P2 |
| Исправлен ретраем | `firstStatus ≠ passed`, `lastStatus = passed` | Сколько «зелени» дал ретрай | Плитка | P2 |
| Регресс | `firstStatus = passed`, `lastStatus ≠ passed` | Тест был зелёным и сломался | Счётчик + список | P2 |
| Новые падения | путь не падал в предыдущем отчёте, падает в этом | Что сломалось именно сейчас | Список | P2 |
| Исправленные | падал в предыдущем, прошёл в этом | Эффект работ | Список | P2 |

### 4.2. Стабильность и ретраи

| Метрика | Как считать | Зачем | Визуал | Приоритет |
| --- | --- | --- | --- | --- |
| Флаки-тест | в окне есть и `passed`, и `failed/broken` | Главный сигнал нестабильности | Счётчик + таблица | P1 |
| Доля флаки | флаки / `C` | Сравнение отчётов и наборов | Плитка | P1 |
| Stability score теста | `passedRuns / allRuns` | Устойчивость конкретного теста | Колонка в таблице | P1 |
| Число переключений | число смен статуса в хронологии | Насколько «дёргается» тест | Сортировка топа | P2 |
| Объём ретраев | `runs - 1` на путь | Нагрузка на прогон | Плитка | P2 |
| Успех после ретрая | пути, ставшие `passed` после падения, / пути с ретраями | Помогают ли ретраи | Плитка | P2 |
| Топ нестабильных | сортировка по переключениям и ретраям | Кого чинить первым | Таблица | P1 |

Все метрики этого блока требуют сырых запусков. Без них максимум можно показать «есть несколько
запусков» по `resultId`/датам, но не переходы.

### 4.3. Длительность

| Метрика | Как считать | Зачем | Визуал | Приоритет |
| --- | --- | --- | --- | --- |
| Суммарное время | `Σ durationMs` | Текущая плитка | Плитка | Есть |
| Среднее | `Σ / timed` | Текущая подпись | Плитка | Есть |
| p50 / p90 / p95 / p99 / max | перцентили по `durationMs > 0` | Хвост важнее среднего | Плитка/таблица | P1 |
| Гистограмма длительностей | бакеты `<1s`, `1–5s`, `5–15s`, `15–60s`, `>60s` | Форма распределения | Histogram | P1 |
| Топ медленных | топ-N по `durationMs` | Есть топ-8 | Список | Есть |
| Время по наборам | `Σ` и `p90` на набор | Где теряется время | Бары | Частично |
| Время по статусам | `p90` для passed vs failed | Падения медленнее? | Две линии | P2 |
| Доля таймаутов | regex по `message` (`timeout`, `timed out`, `TimeoutException`) | Инфраструктура или продукт | Плитка | P2 |
| Дельта к предыдущему отчёту | `p90` и `Σ` минус предыдущий | Ускорение/замедление | Δ в таблице | P2 |
| Wall-clock и параллелизм | `max(end) − min(start)` и `Σ / wall-clock` | Эффективность прогона | Плитка | P2 (нужны сырые запуски) |

### 4.4. Падения и дефекты

| Метрика | Как считать | Зачем | Визуал | Приоритет |
| --- | --- | --- | --- | --- |
| Failed / broken | `F`, `B` | Дефект продукта vs дефект теста (аналог категорий Allure) | Донат, плитка | Есть частично |
| Подпись ошибки | нормализованный `message` | Схлопывает «одинаковые» ошибки с разными ID/строками | Топ-таблица | P1 |
| Топ-10 подписей и Парето | доля топ-10 от всех падений | 80 % падений в 10 причинах? | Bar + накопленная линия | P1 |
| Распределение `failureReason` | группировка по причине | Есть | Таблица | Есть |
| Покрытие анализом | `(F+B с failureReason) / (F+B)` | Сколько падений реально разобрано | Прогресс/плитка | P0 |
| Долг анализа | падения без причины/комментария по владельцу и набору | Кому и что разбирать | Таблица | P1 |
| Возраст падения | `firstSeen` пути в фазе | Новое или тянется | Колонка | P2 |
| Новые / известные падения | сравнение с предыдущим отчётом | Шум vs регресс | Плитка | P2 |
| Пустые сообщения | доля `message = null` среди падений | Качество данных автоматизации | Плитка | P2 |
| Концентрация по набору/владельцу | доля падений | Где огонь | Таблица | P2 |

**Нормализация сообщения** — ключевая деталь. Сейчас «Уникальные ошибки» группируют по точной
строке, поэтому `expected: <403> but was: <500> at ...:87` и `...:92` — разные ошибки. Предлагаемая
подпись: lower-case, удалить timestamp/UUID/hex/числа/`file:line`/URL, обрезать до 120 символов,
затем группировать. Это даёт стабильный «отпечаток» и основу для истории дефектов.

### 4.5. Владельцы и ответственность

| Метрика | Как считать | Зачем | Визуал | Приоритет |
| --- | --- | --- | --- | --- |
| Матрица владельцев | статусы и проценты по владельцу | Есть | Таблица | Есть |
| Доля без владельца | `owner = null` / `C` | Качество каталога | Плитка | P1 |
| Падения на владельца | `F+B` по владельцу | Нагрузка на разбор | Таблица | Есть частично |
| Покрытие анализом по владельцу | разобрано / падения | Кто закрывает анализ | Колонка | Есть частично |
| Флаки и p90 по владельцу | из блоков 4.2 и 4.3 | Полный профиль зоны | Колонка | P2 |
| `fullResponsibility` vs `owner` | сравнение полей | Ответственность в каталоге и в запуске расходятся | Список расхождений | P2 |

### 4.6. Покрытие, свежесть и теги

| Метрика | Как считать | Зачем | Визуал | Приоритет |
| --- | --- | --- | --- | --- |
| Покрытие каталога | `E / C` | Дублирует 4.1 | Прогресс | P0 |
| Никогда не запускался в фазе | нет запусков за фазу | Мёртвый каталог | Список | P1 |
| Устаревший «зелёный» | последний запуск старше N дней | Отчёт опирается на старые данные | Счётчик | P1 |
| Запуски вне каталога | есть `TestResult`, нет `AutomatedTest` | Слепые зоны и повод для Harvest | Плитка + список | P1 |
| Новые тесты в отчёте | первый запуск пути в этом отчёте | Что добавили | Список | P2 |
| Прохождение по тегу | `P / (P+F+B+S)` по тегу | smoke/regression/api/ui | Таблица | P1 |
| Матрица тег × статус | строки — теги, столбцы — статусы | Быстрый обзор | Heatmap | P2 |
| Severity / critical pass rate | по тегам `severity:*` или новому полю | Критичные тесты не должны падать | Плитка | P3 |

## 5. Статистика по всем отчётам фазы

**Реализовано в MVP:** KPI, сравнение отчётов, тренд, матрица «тест × отчёт», подписи ошибок,
владельцы, наборы, гигиена данных, lifecycle и возраст текущих падений с MTTR. Остальные строки
таблицы — следующие шаги.

| Метрика | Как считать | Зачем | Визуал | Приоритет |
| --- | --- | --- | --- | --- |
| KPI фазы | отчёты, каталог, `passedOnce`, `neverPassed`, `alwaysFailed`, общий pass rate, покрытие | Ответ на «фаза готова?» | Ряд плиток | P0 |
| Накопительный результат | прошли хотя бы раз / каталог | Есть | Прогресс | Есть |
| Сравнение отчётов | по каждому: `P/F/B/S/N`, pass rate, coverage, p90, flaky, анализ, Δ к предыдущему | Главный рабочий экран | Таблица с сортировкой | P0 |
| Тренд прохождения | pass rate по отчётам в хронологии | Растём или падаем | Линия + стек | P0 |
| Тренд падений | `F+B` по отчётам | Динамика дефектов | Линия/бар | P1 |
| Матрица тест × отчёт | строки — тесты, столбцы — отчёты, цвет — статус | Видно, где тест сломался и починился | Heatmap | P0 |
| Переходы статусов | pass→fail, fail→pass между отчётами | Поток качества | Sankey/стрелки | P2 |
| Реестр нестабильных | тесты, менявшие статус в фазе | Кого чинить | Таблица | P1 |
| Категории: нестабильный / регресс / исправлен / всегда красный / никогда не запускался | классификация по истории отчётов | Понятный рабочий список | Фильтры + счётчики | P1 |
| Прогресс покрытия | новые протестированные пути по отчётам | Растёт ли покрытие | Area/линия | P1 |
| Никогда не проходил | путь ни разу не `passed` за фазу | Риск релиза | Список | P0 |
| Всегда падает | все запуски `failed/broken` | Хронические дефекты | Список | P1 |
| Владельцы в фазе | падения, pass rate, анализ, flaky по владельцу | Сводка по зонам | Таблица | P1 |
| Наборы в фазе | pass rate, p90, падения по `suiteName` | Где проблемные наборы | Таблица | P1 |
| Подписи ошибок в фазе | топ, новые/известные, Парето | Приоритет фиксов | Таблица | P1 |
| Долг анализа в фазе | % падений без `failureReason` | Управляемость качества | Прогресс | P1 |
| Время и ёмкость | `Σ` по отчётам, p90, wall-clock, параллелизм | Планирование прогонов | Линия/плитки | P2 |
| Гигиена данных | запуски вне каталога, чужой `circuit`, дубли, пересечение окон отчётов, пустые owner/message | Доверие к цифрам | Аккордеон | P1 |
| Risk / readiness score | взвешенная свёртка метрик | Одна цифра для релиза | Gauge | P3 |
| Сравнение фаз | та же среда, предыдущая фаза, дельта | Прогресс между релизами | Таблица | P3 |

### 5.1. Матрица «тест × отчёт» — главный кандидат

Почему она важнее ещё одного доната:

- один экран отвечает на вопросы «что сломалось между отчётами», «что починили», «что никогда
  не запускалось»;
- использует уже существующие данные (каталог + запуски в окнах отчётов);
- хорошо масштабируется: строки группируются по наборам и сворачиваются, столбцы — отчёты.

Формат ответа лучше делать компактным: ячейка — код `p/f/b/s/n`, а не объект. Иначе
1000 тестов × 30 отчётов = 30 000 объектов в JSON. Коды + отдельный словарь статусов дают
десятки килобайт вместо сотен.

### 5.2. Гигиена данных

Это не «красивая аналитика», но именно она защищает от неверных выводов:

- **запуски вне каталога** — сколько путей и запусков не видны в отчётах;
- **чужой `circuit`** — запуски проекта, не попавшие в фазу из-за окружения;
- **дубли** — одинаковые `path + startDate` (следствие отсутствия идемпотентности);
- **пересечение окон отчётов** — сколько запусков учитывается в двух и более отчётах;
- **пустые `owner` / `message`** — качество входных данных;
- **объём приёма** — запусков в день, пики, «провалы» (автоматизация не присылала данные).

Последний пункт особенно полезен: «ноль падений» может означать не качество, а отсутствие запусков.

### 5.3. Risk / readiness score

Одна цифра удобна для релизного решения, но опасна как единственный критерий. Предлагаемая
эвристика (веса настраиваются):

```text
score = 100
      − 30 × (1 − effectivePassRate)
      − 20 × criticalFailureShare
      − 15 × noRunShare
      − 15 × flakyShare
      − 10 × analysisDebt
      − 10 × min(p95 / p95Target, 1)
```

Смысл: штраф за падения, критичные падения, непрогнанное, нестабильное, неразобранное и медленное.
Score всегда показывается вместе с составляющими — иначе им нельзя управлять.

## 6. Свои идеи, которых нет в Allure

1. **Stale green / «зелёный по старой данных».** Отчёт `passed`, но последний запуск упал или
   старше N дней. Уникально для этой модели, где отчёт — окно, а не сборка.
2. **Матрица тест × отчёт.** Аналог истории, но сразу по всей фазе и с группировкой по наборам.
3. **Гигиена данных.** Отдельный блок доверия к отчёту: вне каталога, дубли, пересечения окон.
4. **Долг анализа как SLA.** Не просто «сколько без причины», а «сколько дней висит» и «кто
   держит».
5. **Wall-clock efficiency.** Сумма длительностей против реального времени фазы: сколько
   параллелизма было и где простой.
6. **Coverage-adjusted pass rate.** Не один процент, а пара «прохождение + покрытие»: 100 %
   прохождения при 40 % покрытия — не 100 % качества.
7. **Trust score отчёта.** Свёртка свежести, покрытия, анализа и флаки: можно ли верить зелёному
   отчёту.
8. **Quality Gate по тегам.** `smoke` — 100 %, `critical` — без падений, `no_run` — не больше X %.
9. **Карта пересечений отчётов.** Показать, какие отчёты делят одни и те же запуски; защищает от
   двойного счёта в сравнительной таблице.
10. **Sankey переходов статусов** между отчётами: pass→fail, fail→pass, pass→skip. Наглядно, но
    сложнее в реализации, поэтому после матрицы.

## 7. Предлагаемые экраны

### 7.1. Аналитика отчёта v2

```text
[KPI] эффективный pass rate | покрытие | failed+broken | p90 | флаки | stale green
[Статусы: донат]            [Прохождение по наборам: бары]

```

### 7.2. Аналитика фазы

```text
[KPI] отчёты | каталог | прошли хотя бы раз | никогда не проходили | flaky | покрытие
[Quality Gate: pass/fail по правилам]

[Топ подписей ошибок] [Владельцы/наборы]

```

Навигация: на странице фазы (`ReportsPage`) добавить кнопку «Аналитика фазы»; маршрут
`/phase/:phaseId/analytics`. Текущий regex в `App.jsx` уже разбирает `/analytics` только после
`/report/:id`, поэтому его нужно расширить и аккуратно обновить `getPath`.

## 8. API и архитектура

### 8.1. Эндпоинты

| Метод и путь | Статус | Назначение |
| --- | --- | --- |
| `GET /api/phases/:phaseId/analytics` | Реализовано | KPI, сравнение отчётов, матрица, владельцы, наборы, ошибки, гигиена |
| `GET /api/phases/:phaseId/analytics/matrix` | Не реализовано | Вынести матрицу отдельно, если ответ станет большим |
| `GET /api/reports/:reportId/analytics` | Не реализовано | Расширенная аналитика отчёта (перцентили, флаки, подписи, долг) |
| `GET /api/reports/:reportId/runs?path=` | Не реализовано | История запусков для drill-down (v3) |

Для MVP матрица включена в общий ответ: один запрос на страницу и одна согласованная картина.
Если каталог вырастет до тысяч тестов, матрицу стоит вынести в отдельный эндпоинт с пагинацией
по наборам — сейчас она отдаётся компактными кодами `p/f/b/s/n`.

Пример формы ответа фазы:

```json

    "reports": 12, "catalog": 840, "executed": 780, "passedOnce": 760,

    "passRate": 0.81, "coverage": 0.93, "totalRuns": 940
```

### 8.2. Модуль и расчёт

- Реализован read-only модуль `analytics` (`controller` + `service`): контроллер — HTTP, сервис —
  правила. Отдельный репозиторий не нужен: запросы идут через существующие `PhasesService`,
  `ReportsRepository`, `ResultsRepository`, `TestsRepository`. Не складывать всё в `ReportsService`:
  он отвечает за представление отчёта.
- `dayStart` / `dayEnd` / `parseDateOnly` вынесены в `common/dates/day-range.ts`.
- Запросы: фаза + отчёты + видимый каталог + все запуски за период фазы (один запрос с GiST),
  дальше группировка в памяти. Нет запроса на каждый отчёт — это был бы N+1.
- Для гигиены запуски запрашиваются **без** фильтра по `circuit`; окружение фазы применяется
  в памяти, поэтому видны и «чужие» запуски.
- Перцентили считаются в памяти (ближайший ранг), чтобы не дублировать формулу на клиенте.
- Кэширование не добавлено: на текущих объёмах достаточно индексов. При росте — `ETag` от
  `phase.updatedAt` + `max(TestResult.createdAt)`.
- Валидация: `ParseBigIntPipe`, DTO для фильтров, глобальный `ValidationPipe` уже включён.
- Ошибки: 404 для несуществующей фазы/отчёта, как в текущих сервисах.

### 8.3. Клиент

- `dataService.getPhaseAnalytics(phaseId)` и `getReportAnalytics(reportId)`; запросы — через
  `Promise.all`, как в `getData`.
- Тяжёлые агрегаты считает сервер; клиент только форматирует и сортирует. Это снимает риск
  расхождения формул между экранами.
- `PhaseAnalytics.jsx` грузить лениво (`React.lazy` + `Suspense`), чтобы не увеличивать стартовый
  бандл; SVG-графики из `SimpleCharts` подключаются вместе с этим чанком.
- Матрицу рисовать CSS Grid, а не библиотекой графиков: тысячи ячеек дешевле и доступнее
  (фокус, `title`, aria).
- Не кодировать статус только цветом: подпись/иконка/паттерн — иначе матрица нечитаема для
  дальтоников и в светлой теме.

## 9. Чем рисовать

Графики аналитики отчёта и фазы перерисованы на собственные SVG-компоненты
([`components/charts/`](../src/components/charts/)); `SimpleCharts.jsx` остаётся barrel-точкой,
а реализации разложены по файлам `StackedBarChart.jsx`, `ColumnChart.jsx`, `LineChart.jsx`,
`DonutChart.jsx`, `BoxPlot.jsx`, `DurationProfile.jsx`, `ParetoChart.jsx`. `@ant-design/charts` больше
не импортируется.

| Визуал | Где | Реализация |
| --- | --- | --- |
| Stacked bar | Статусы по отчётам, длительности по бакетам, владельцы | `SimpleCharts.StackedBarChart` |
| Column | Стабильность, запуски на тест, возраст падений | `SimpleCharts.ColumnChart` |
| Line | Pass rate и coverage по отчётам | `SimpleCharts.LineChart` |
| Donut | Lifecycle тестов | `SimpleCharts.DonutChart` |
| Duration profile | Разброс длительности по наборам (min–max, p25/p50/p75/p90) | `SimpleCharts.DurationProfile` |
| Pareto | Подписи ошибок (частота + накопленная доля) | `SimpleCharts.ParetoChart` |
| Полосы/донат/матрица | Простые статусы, сводка, тест × отчёт | SVG/CSS |
| Heatmap | Теги × статусы, крупная матрица | Следующий этап |
| Sankey | Переходы pass→fail между отчётами | Следующий этап |

Правила:

- SVG рисуется в `viewBox`, тянется по ширине карточки и использует CSS-переменные темы;
- подписи/легенды/таблицы остаются доступными, `title` даёт подсказки;
- аналитика отчёта и фазы — ленивые маршруты, поэтому графики не попадают в стартовый бандл;
- вместо тяжёлой chart-библиотеки используется ~13 КБ собственного кода.

| Этап | Что | Схема/API | Оценка |
| --- | --- | --- | --- |
| 0 | Этот документ, обновление индекса кода | Нет | Сделано |
| 1 | Отчёт: эффективный pass rate, покрытие, skip, p50/p90/p99, гистограмма, наборы, подписи ошибок, долг анализа | Нет, клиент | Сделано (MVP) |
| 2 | Фаза: KPI, сравнение отчётов, тренд, матрица, гигиена, lifecycle, возраст падений | Новый read-only API | Сделано (MVP) |
| 3 | История: флаки, ретраи, первый/последний запуск, новые/известные, stale green | API истории запусков | M |
| 4 | Quality Gate, risk score, экспорт CSV/PNG | Настройки порогов | S–M |
| 5 | Allure-паритет: severity, labels, шаги, вложения, параметры, launch/build | Миграции + приём | L |

Приоритеты:

- **P0** — то, что меняет выводы: эффективный pass rate, покрытие, `no_run`, матрица, сравнение
  отчётов, «никогда не проходил».
- **P1** — диагностика: перцентили, подписи ошибок, флаки, долг анализа, гигиена.
- **P2** — динамика: тренды, новые/известные, stale green, wall-clock.
- **P3** — модельные расширения и одна сводная цифра.

## 11. Критерии приёмки

1. Инварианты: `P + F + B + S + N = C`; сумма по матрице в столбце равна `total` отчёта;
   `passedOnce` фазы равен числу путей, у которых хотя бы в одном отчёте `passed`.
2. Деление на ноль не даёт `NaN`: пустой каталог → `null`/`0` и пустое состояние.
3. Перцентили определены однозначно (метод и округление) и совпадают на сервере и клиенте,
   если считаются в двух местах.
4. `no_run` и `skipped` не попадают в перцентили длительности.
5. Окна отчётов и часовые пояса: расчёт — в UTC по дню, отображение — локальное; граница дня
   не «съедает» запуски.
6. Запуски вне каталога видны в гигиене, но не искажают статусы отчёта.
7. Фаза на 1000 тестов × 30 отчётов отвечает за приемлемое время (ориентир — до 1–2 с) без N+1.
8. Матрица имеет текстовые подписи/`aria-label`, статус читается без цвета, наборы сворачиваются
   кнопками; полноценная клавиатурная навигация по ячейкам — за пределами MVP.

## 12. Открытые вопросы

1. Главный сценарий: релизное решение (gate) или ежедневный разбор падений? От этого зависит,
   что выносить на первый экран.
2. Оставляем ли правило «passed побеждает» в отчёте? Для аналитики в любом случае нужен
   `latestStatus` рядом.
3. Откуда брать severity: тег `severity:*`, поле каталога или отдельная таблица?
4. Пересечение окон отчётов — намеренная возможность или ошибка планирования? Нужна ли валидация
   при создании?
5. Повторный `POST /results` — это ретрай или отдельный прогон? От ответа зависит трактовка
   flaky и retry-метрик.
6. Какие объёмы ожидаются (тесты × отчёты × запуски) и сколько истории хранить?
7. Нужен ли экспорт (CSV, PNG, ссылка на отчёт) и кому?
8. Есть ли роли/ответственные, для которых нужен отдельный вид (QA lead, разработчик, менеджер)?
